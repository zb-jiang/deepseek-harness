## 1. 背景与目标

### 1.1 现状

汉云当前的认证体系以 Supabase Auth 为根：

| 组件                   | 现状                                                                                        | 代码位置                                               |
| -------------------- | ----------------------------------------------------------------------------------------- | -------------------------------------------------- |
| 登录                   | 前端持 Supabase anon key 直连 Supabase Auth                                                    | `platform-user-api`（volatile 配置）                   |
| 验签 ① 员工端             | enterprise profile 内 `platform-user-console` 插件，jose 库 + Supabase JWKS，校验 iss + exp + sub | `platform-user-console/src/index.ts:258-263`       |
| 验签 ② web-console 后端  | Java NimbusJwtDecoder + Supabase issuer                                                   | `apps/web-console/backend/.../SecurityConfig.java` |
| 验签 ③ flowable-engine | Java NimbusJwtDecoder + Supabase issuer，V1 明确不校验 aud                                      | `apps/flowable-engine/.../SecurityConfig.java`     |
| 用户治理                 | platform_users 表：审批/禁用/锁定/角色，Web Console 承载写操作                                            | `platform-user` 包                                  |
| 身份关联键                | `auth_subject` = Supabase `sub`                                                           | `platform-user/src/index.ts`                       |

**核心问题**：账号根在企业外部（Supabase 云），企业实施时员工不可能为汉云单独记一套密码；且换任何认证源都要同时动三处验签点。

### 1.2 已达成的共识决策

| #  | 决策                                                              | 说明                        |
| -- | --------------------------------------------------------------- | ------------------------- |
| D1 | 认证交给企业 IM（钉钉/飞书/企业微信扫码），**身份治理保留 platform_users**（批量导入 + 现有审批流） | 员工用公司 IM 登录，汉云不存密码        |
| D2 | 登录成功后，**汉云自签发"内部通行证"**，三处验签点从此只认自家通行证                           | 换 IM 平台只动登录页与发证服务，验签点永不再动 |
| D3 | 通行证 aud 采用**最粗颗粒**：固定值 `yunhan-internal`                        | 只做"防出体系"，不做细颗粒门禁          |
| D4 | **不做权限集中管控**：员工能进哪些 SOR、在各 SOR 的权限，由各 SOR 自控                    | 通行证不承担授权职责                |
| D5 | backend profile 现状**不验任何 token**（内网信任），机器调用将来走"机器通行证"（服务账号形态）   | 服务账号 = 机器法人账户，非人类代办通道     |
| D6 | 短时效 + jti 作为主要安全手段                                              | 替代细颗粒 aud 的兜底             |

## 2. 总体架构

### 2.1 目标链路

```
┌─────────────┐    扫码/回调     ┌──────────────────┐
│ 企业 IM IdP  │ ──────────────→ │  汉云发证服务      │
│ 钉钉/飞书/企微 │   验证通过+用户ID │  (token-issuer)   │
└─────────────┘                 └────────┬─────────┘
                                         │ 签发内部通行证 (JWT)
                              ┌──────────┴──────────┐
                              │  platform_users 影子目录 │
                              │  auth_subject = IM userid │
                              └──────────┬──────────┘
                                         │
     员工端 ──带通行证──→ 本地 webserver ──转发──→ flowable-engine
        │                                        │
        └────────── 带通行证 ──→ web-console 后端 ─┘

     三处验签点（员工端 profile / web-console / engine）
     只认汉云发证服务的 JWKS，iss = yunhan, aud = yunhan-internal
```

### 2.2 分层职责

| 层              | 职责                 | 持有什么             |
| -------------- | ------------------ | ---------------- |
| 企业 IM IdP      | 证明"你是公司员工"（扫码登录）   | 员工的真实身份与在职状态     |
| 汉云发证服务         | 验证 IM 回调 → 签发内部通行证 | **签名私钥（唯一关键资产）** |
| platform_users | 治理：审批、禁用、锁定、角色     | 用户档案（影子目录）       |
| 三处验签点          | 验通行证真伪后放行          | 只有公钥（JWKS）       |
| 各 SOR          | 各自的认证与授权           | 各自的账号体系          |

## 3. 工作项一：发证机制与通行证格式规范

### 3.1 通行证格式规范（JWT Claims 契约）

所有汉云体系内的服务按本契约验签，每个字段含义与验签规则如下：

| Claim                    | 必填 | 值                             | 验签点行为                           | 说明                        |
| ------------------------ | -- | ----------------------------- | ------------------------------- | ------------------------- |
| `iss`                    | 是  | `yunhan`                      | 必须等于 `yunhan`                   | 签发方标识                     |
| `aud`                    | 是  | `"yunhan-internal"`           | 必须等于该值（V1 可仅员工端校验，三处对齐后全量启用）    | 通行证只能被汉云体系内的服务接受；流出到体系外无效 |
| `sub`                    | 是  | platform_users 主键或稳定用户 ID     | 非空；作为流程身份（Flowable assignee 依据） | 员工唯一标识                    |
| `loginName`              | 是  | 员工登录名（与 IM userid 对应）         | 展示/日志用                          | 可读身份                      |
| `platformRoles`          | 是  | string[]，如 `["system_admin"]` | 展示用；**授权仍以各服务本地查询为准**           | 角色冗余只为展示与快速判断，不作为集中授权依据   |
| `employeeNo` / `orgUnit` | 否  | 工号 / 部门                       | 展示用                             | 减少重复查询                    |
| `iat` / `exp`            | 是  | 签发/过期时间                       | exp 必须未过期；容忍 ±60s 时钟偏差          | 见 3.2 有效期策略               |
| `jti`                    | 是  | 唯一 ID                         | V1 不强制查黑名单；预留吊销能力               | 离职/紧急吊销时按 jti 拉黑          |
| `typ`                    | 是  | `user` 或 `machine`            | 机器通行证仅限服务端使用                    | 区分人与机器                    |

**有效期策略**：

| 通行证类型                    | 有效期          | 续期方式                         |
| ------------------------ | ------------ | ---------------------------- |
| 用户通行证                    | 4~8 小时（实施时定） | 过期前静默续签一次；续签需当前证仍有效且用户未被禁用   |
| 机器通行证（backend task、服务账号） | 12~24 小时     | 常驻服务自动续签；密钥泄露可立即按 jti/签发序列吊销 |

**禁用即失效**：`platform_users.status` 置 `disabled` 后，续签接口拒绝发新证；已发短时效证自然过期（这也是有效期不宜超过 8 小时的原因）。

### 3.2 发证服务设计

**形态：独立部署的轻量 HTTP 服务**（`apps/token-issuer`，与 web-console 在仓库中的地位同级），**不是 Cordis 插件**。理由：

1. **启动顺序**：发证服务是登录的前提，必须在一切业务运行时（员工端 profile / web-console / engine）之前可用；Cordis 插件生命周期跟随 profile，profile 未加载或重载期间认证即瘫痪——依赖方向不能反
2. **部署位置**：发证服务握有签名私钥，是服务器端单例公共基础设施；而 Cordis 插件的主要宿主（员工端 profile）分布在每台员工电脑上，私钥绝不能下发到员工机器
3. **攻击面**：私钥资产要求最小暴露面与独立重启/升级；与几十个业务插件共享进程会放大攻击面（见风险 R2 的缓解前提）
4. **零业务依赖**：认证基础设施只被依赖、不依赖业务运行时；Cordis 插件天然反向依赖 harness 能力注入

**实现建议**：Node.js/TypeScript + `jose`（与员工端验签同库，签发/验签算法同源，避免跨语言对齐签名问题）；预计 300~500 行代码，独立端口、独立进程、独立生命周期。备选方案为第二个 Spring Boot 服务（Java 侧已有 NimbusJwtDecoder 经验）——语言选择留实施时定，但**独立进程形态没有余地**。

**接口清单**：

| 接口                                           | 方法   | 说明                                                     |
| -------------------------------------------- | ---- | ------------------------------------------------------ |
| `/auth/jwks.json`                            | GET  | 公钥集合。三处验签点的唯一依赖；支持多 key 轮换                             |
| `/auth/token`                                | POST | 签发通行证。入参：IM 平台回调凭证（code）或有效的旧通行证（续签）；出参：通行证 JWT        |
| `/auth/revoke`                               | POST | 按 jti 吊销（管理员操作，写吊销名单）                                  |
| `/auth/.well-known/openid-configuration`（可选） | GET  | 标准发现文档，方便 Java 侧 `JwtDecoders.fromIssuerLocation` 直接使用 |

**密钥管理**：

- 私钥只存在于发证服务，ES256/RS256 非对称签名（与现有 Supabase JWKS 同类技术，三处验签点代码改的是"公钥地址"，不是验签框架）
- 轮换：JWKS 同时挂新旧两把公钥，新证用新私钥签，旧证自然过期后下线旧钥——轮换对验签点透明
- 私钥文件权限与备份策略在实施时细化；不与业务数据库同机存放

### 3.3 三处验签点改造（改动最小化的关键）

| 验签点                         | 现状                                                | 改造内容                                          | 工作量 |
| --------------------------- | ------------------------------------------------- | --------------------------------------------- | --- |
| 员工端 `platform-user-console` | jose + Supabase JWKS 地址（volatile 配置）              | JWKS 地址与 iss 换成汉云发证服务；增加 aud 比对               | 小   |
| web-console 后端              | `JwtDecoders.fromIssuerLocation(supabase-issuer)` | issuer 配置换成汉云发证服务地址；Spring 自动拉 JWKS           | 小   |
| flowable-engine             | 同上                                                | 同上；同时把 V1 注释中"不校验 aud"升级为校验 `yunhan-internal` | 小   |

**架构回报**：这次改造完成后，**再换 IM 平台（钉钉→飞书等）时，三处验签点零改动**——只动登录页和发证服务的"IM 适配器"。

### 3.4 机器通行证（服务账号）

- backend profile、未来的 SOR 转换器等常驻程序，以 `typ=machine` 的通行证调用体系内服务
- 机器通行证**不需要**"代办声明"：AI/机器触发的动作本来就应记在"汉云平台"名下，与老 SOR"认证授权一致"的现实不冲突
- `flowable-engine` SecurityConfig 注释中"V2 收紧为静态 service token"的计划，由机器通行证实现（ engine 侧为机器通行证开独立的验签路径或直接复用同一 JWKS）

## 4. 工作项二：与企业 IM（钉钉/飞书/企业微信）打通

### 4.1 登录流程

```
员工打开云汉员工端
  → 登录页展示 IM 扫码二维码（或跳转 IM 授权页）
  → 员工在钉钉/飞书/企微 App 中确认
  → IM 回调汉云登录服务（携带一次性 code）
  → 发证服务后端用 code 换取 IM 侧用户身份（userid、姓名、部门）
  → 以 IM userid 查 platform_users.auth_subject：
       命中 → 检查 status（pending_approval 拒绝并提示待审批；disabled 拒绝）
       未命中 → 首登 JIT 建档进 pending_approval（复用现有审批流）
  → 签发内部通行证，员工端持证进入工作台
```

要点：

- **关闭自注册通道**：企业环境下员工不能自助开户，未导入的员工首登只建"待审批"影子档案
- `auth_subject` 字段语义从"Supabase sub"改为"IM 平台 userid"（组织内稳定标识）——该字段本就设计为抽象关联键，属数据口径调整而非结构变更
- 企业微信登录接口自成体系，实施时按选定平台写一个 **IM 适配器**（code 换 userid 的协议差异全部收在这一层）

### 4.2 platform_users 治理职能保持不变

| 治理动作  | 现状机制                      | 变化                            |
| ----- | ------------------------- | ----------------------------- |
| 批量导入  | 管理员导入员工名册（含 IM userid）    | 不变；auth_subject 列改存 IM userid |
| 开户审批  | pending_approval → active | 不变                            |
| 禁用/锁定 | status 四态                 | 不变；禁用后通行证续签即断                 |
| 角色管理  | platformRoles 三角色         | 不变                            |

### 4.3 入离转（JML）联动（概要）

- **入职**：IM 平台建号 → 名册导入 platform_users（active 或走审批）→ 通行证可用
- **转岗**：IM 部门变化 → 定时同步或 webhook → org positions 更新 → DMN 组织审批路由自动生效（该链路已落地）
- **离职**：IM 删号/禁用 → 通行证续签失败自然失效 + platform_users 置 disabled → 对应表服务级联失效（见工作项三）

## 5. 工作项三：SOR 门禁对应表服务（设计概要）

> **定位**：把汉云内部通行证与各 SOR 系统的账号"翻译"起来——员工拿通行证进门，对应表告诉他"在这个系统里你叫什么"。
> **铁律**：只存身份映射、**不存凭据**（密码/密钥）。凭据保管库只在遇到完全封闭的 SOR 时按需另建，且应随 SOR 升级趋向清空。

### 5.1 一个关键前提：映射怎么设计，取决于企业内部 SSO 方案

企业内部存在一套自己的 SSO 体系（**不是**钉钉/飞书/企业微信——IM 只承担"扫码证明你是谁"这一步）。SOR 系统历史上大多已经接入了这套内部 SSO 或它的前身（AD/LDAP 域账号）。因此对应表的映射模式**不能现在拍死**，必须等企业内部 SSO 方案明确后按情形选型：

| 情形 | 企业内部 SSO 的形态 | 对应表映射模式 | 工作量 |
|---|---|---|---|
| ① SOR 已联邦到内部 SSO | 标准 IdP（OIDC/SAML），SOR 直接认它的票 | 汉云通行证 ↔ 内部 SSO 账号做**同名/ID 链式映射**，SOR 侧零改动 | 小 |
| ② 内部 SSO = 统一目录 | AD/LDAP，SOR 用域账号登录 | 同名映射（`汉云账号 = 域账号`），对应表退化为一张同名对照 | 小 |
| ③ 无统一体系 | 各 SOR 自有账号 | 逐 SOR 摸底身份入口后逐个映射（见 5.2 摸底矩阵） | 中~大，逐个来 |

> 设计含义：**对应表服务先建"骨架"（登记表 + 映射表 + JML 联动），映射策略做成可插拔**——骨架不依赖企业 SSO 方案，策略插件等方案明确后逐个填充。

### 5.2 SOR 登记表（sor_registry）——摸底结果的载体

每个接入的 SOR 登记一行，其中"身份入口类型"是最值钱的字段：

| 字段 | 说明 |
|---|---|
| `sorName` | SOR 名称 |
| `identityEntryType` | **身份入口类型**：`ldap-domain`（LDAP/AD 域账号）/ `trusted-header`（可信代理头）/ `api-operator`（API 操作人字段）/ `closed`（完全封闭）/ `federated`（已联邦到内部 SSO） |
| `mappingStrategy` | 映射策略：同名 / 显式对照表 / 待摸底 |
| `probeEndpoint` | 连通性探测地址（复用现有 probeConnectivity 实现） |
| `ownerContact` | SOR 责任人 |

**摸底结论（已达成共识）**：历史 SOR 的认证与授权是焊死的（谁登录按谁的权限办事），改造 SOR 来适配方案不现实——方案必须绕着"它有什么现成入口"来设计。四个入口按侵入度从低到高：

1. **LDAP/AD 域账号集成**（老系统极常见，改配置即接）
2. **可信代理头注入**（部署在反向代理后的系统，改配置）
3. **API 操作人字段**（ERP 类开放接口常带 operator/userId 参数，纯调用）
4. **完全封闭**（三选一：服务账号直连且审计落机器账号 / 密码代持兜底 / 推动厂商改造）

### 5.3 映射表（federated_identities）

```
platform_user_id  ↔  sor_id（哪个 SOR）  ↔  sor_user_id（在那边的账号）
                        + status + 同步时间戳
```

- **自动建**：SOR 登记后，按映射策略批量初始化（同名策略直接生成；显式对照走导入模板）
- **自动改**：IM 转岗 webhook → platform_users/org positions 更新 → 受影响的映射行联动更新
- **自动删（失效）**：IM 离职 → platform_users 置 disabled → 该员工全部映射行置停 + 通知各 SOR 管理员
- **只存 ID**：即使 `closed` 类 SOR，映射表也只存账号名的对应关系；密码属凭据保管库职责，永不进入本表

### 5.4 人的使用与机器调用的分野（已达成共识）

| 场景 | 通行方式 | 审计落点 |
|---|---|---|
| 员工交互使用 SOR | 必须落到个人身份（走入口 ①②③）；真封闭才密码代持 | 个人 |
| AI/backend task 调用 SOR | 机器通行证（`typ=machine`，见 3.4），不需要代办声明 | "汉云平台"机器账号——语义本来就成立，与老 SOR"认证授权一致"不冲突 |

## 6. 实施步骤

| 阶段 | 内容                                                    | 前置条件    |
| -- | ----------------------------------------------------- | ------- |
| S1 | 确定企业 IM 平台（钉钉/飞书/企微），在 IM 开放平台建应用、拿凭据                 | 企业决策    |
| S2 | 建发证服务（`apps/token-issuer` 独立服务）：JWKS + 签发 + 续签 + 吊销接口 | —       |
| S3 | 按第 3.1 节固化《通行证格式规范》，评审冻结                              | S2 设计评审 |
| S4 | 三处验签点切换到汉云 JWKS（先员工端，再 web-console，最后 engine；可配置双 issuer 过渡） | S2/S3   |
| S5 | 登录页改造：Supabase 组件 → IM 扫码 + IM 适配器；auth_subject 数据口径切换      | S1/S2   |
| S6 | 存量数据迁移：platform_users 补 IM userid；Supabase 登录通道保留一个观察期后关闭   | S5      |
| S7 | 机器通行证接入 backend profile（替代内网信任/静态 token 计划）                  | S4      |
| S8 | 对应表服务骨架：sor_registry + federated_identities + JML 联动（映射策略可插拔） | 可与 S2 并行；策略填充阻塞于企业内部 SSO 方案明确 |
| S9 | 逐 SOR 摸底身份入口 → 填充映射策略 → 首个 SOR 接入（含转换器模板，如需） | S8 + 企业内部 SSO 方案 |

**回归要点**：三处验签点逐个切换期间，新旧 issuer 可并存（验签点同时接受两把公钥），避免一次性大爆炸切换；切换完成后按员工端端到端场景（登录 → 待办办理 → AI 代办 → web-console 管理）全量回归。

## 8. 三个工作项的关系

```
工作项一（发证服务）──签发通行证──→ 三处验签点
        │
工作项二（IM 打通）──登录入口──→ platform_users（影子目录，auth_subject = IM userid）
        │                              │ JML 入离转联动
        ↓                              ↓
工作项三（对应表服务）←──────────────────┘
        ├── sor_registry：身份入口摸底（LDAP 域账号 / 可信代理头 / API 操作人 / 封闭 / 已联邦）
        ├── federated_identities：通行证 ↔ 企业内部 SSO 账号 ↔ SOR 本地账号
        ├── 映射策略可插拔，选型阻塞于企业内部 SSO 方案（R6）
        └── 机器调用：使用工作项一的机器通行证（服务账号）
```

三个工作项的分工一句话版：**工作项一管"证从哪来"，工作项二管"人怎么进门"，工作项三管"进了门之后在各个 SOR 里叫什么名字"**。对应表服务只存身份映射、不存凭据（钥匙柜按需另建且趋向清空）——本方案把"认证"收敛到汉云通行证之后，对应表服务的职责进一步收窄为"名字翻译"，这正是本次改造为后续 SOR 集成铺路的价值所在。
