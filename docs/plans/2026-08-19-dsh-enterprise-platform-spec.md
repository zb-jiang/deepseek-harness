# DSH 企业级应用平台产品 SPEC

## 文档信息

- 文档状态：Final
- 文档日期：2026-08-19
- 适用读者：产品经理、架构师、后端工程师、前端工程师、测试工程师
- 文档目标：定义 DSH 企业级应用平台的产品边界、核心对象、业务行为和版本范围，使程序员能够据此理解详细产品设计并进一步推导技术实现方案

## 1. 文档范围

本文描述的是 DSH 从个人使用的 Agent Harness 演进为企业级应用平台后的产品设计，不讨论具体技术选型、数据库方案、前后端框架和部署架构。

本文关注的是产品层面的可实现设计，包括平台角色、应用模型、流程模型、待办模型、资源治理、权限体系、审计要求和 V1 范围。

本文不覆盖完整 BPMN 标准、组织架构建模细节、商业化计费、多租户 SaaS 运营和第三方系统适配细节。

## 2. 产品定位

DSH 企业版不是用来替代企业现有专业业务系统，也不是给企业增加一个新的通用聊天入口。

DSH 企业版的定位是一个面向企业内部的 BPIT 平台，即位于现有专业系统之上的统一流程协同层、AI 交互层和集成编排层。

企业内原有 CRM、ERP、OA、HR、财务、研发管理等系统继续承担主数据管理、专业规则执行和专业 GUI 展示；DSH 通过 MCP、skill、知识库和 LLM 能力，将跨系统流程中需要人工参与、人工判断、人工补充、人工确认的节点统一搬到 DSH 中处理。

员工未来主要在 DSH 中接收待办、查看上下文、与 AI 协同、生成结果、提交结果和推动流程流转，而不必频繁在多个系统界面之间切换。

因此，DSH 企业版的核心不是“聊天”，而是“流程驱动的人机协同工作平台”。

## 3. 产品目标

### 3.1 业务目标

1. 为企业提供统一的人机协同入口，承接跨系统流程中所有需要人工参与的环节。
2. 让业务流程以应用为单位沉淀，形成可配置、可治理、可审计、可复用的企业数字化资产。
3. 通过 MCP 接入既有系统，避免重建主数据系统和专业操作界面。
4. 通过 AI 交互降低员工完成复杂业务节点的门槛，提高处理效率和输出质量。
5. 让平台管理员和应用管理员能够治理流程、角色、资源、权限和版本，而不是依赖研发逐次硬编码。

### 3.2 产品目标

1. 提供统一的平台级认证、授权、应用管理和审计能力。
2. 提供应用级流程设计、角色管理、资源编目、节点配置和运行监控能力。
3. 提供面向业务人员的统一待办中心和 AI 任务处理界面。
4. 提供节点输入输出契约和流转前校验能力，确保流程数据可继续被下游节点或外部系统消费。
5. 提供公共资源和应用私有资源并存的治理体系。

## 4. 产品设计原则

### 4.1 平台只承接流程协同，不替代专业系统

DSH 不应承载企业所有专业页面和主数据维护逻辑。凡是已有系统已经稳定承担的专业能力，应通过 MCP 或接口集成接入，而不是在 DSH 内重复建设。

### 4.2 应用是业务域工作台，不是单条流程

一个应用代表一个业务域工作台，包含该业务域下的多条流程、角色、资源和集成，而不是“一个应用只做一条流程”。这样应用边界更稳定，更符合企业内部系统治理方式。

### 4.3 人工节点是平台核心

人工节点不是自动流程的补丁，而是产品核心对象。平台必须优先围绕“人如何理解上下文、如何借助 AI 完成任务、如何输出合格结果、如何被审计”来设计。

### 4.4 流程模型先约束后扩展

V1 不追求完整 BPMN 兼容，而是采用一个受约束但可落地的流程模型，先覆盖企业最常见的线性流转、条件分支、会签或串签、自动处理和人工处理。

### 4.5 资源治理必须先于资源开放

skill、MCP、知识库、LLM 虽然是平台能力，但企业环境下不能默认所有人都可见、可调用、可配置。资源必须先完成编目、命名、版本、权限和发布治理，再面向业务开放。

### 4.6 审计是一级能力，不是附属日志

平台中的注册审批、角色授权、流程发布、节点执行、人工提交、自动调用、外部系统写入和流程终态都必须可审计。没有审计闭环，平台很难进入真实企业环境。

## 5. V1 产品前提

以下内容是 V1 已确定的产品前提。

1. V1 以单企业单实例部署为主，不在核心模型中引入 SaaS 多租户运营能力。
2. V1 依赖数据库、认证和 SSO 等基础中间件能力；产品模型不绑定具体中间件实现。
3. V1 的流程画布采用“受约束流程定义”而不是完整 BPMN 引擎能力。
4. V1 的节点数据流转必须以结构化输入输出契约为基础，允许附带非结构化附件和上下文。
5. V1 先支持“人处理任务”和“自动调用外部能力”两大类节点，不在首版引入过多事件、补偿、复杂编排语义。

## 6. 目标用户与角色

### 6.1 平台级角色

#### 系统管理员

系统管理员负责平台级治理，包括用户审批、平台角色分配、应用创建、公共资源治理、平台审计查看和全局配置管理。

#### 应用管理员

应用管理员负责某个应用内部的配置和治理，包括流程设计、应用角色定义、成员授权、应用资源管理、版本发布和运行监控。

#### 普通用户

普通用户是业务执行人员，只能访问自己有权限进入的应用和流程节点，只能处理分配给自己的待办和查看自己被授权的数据范围。

### 6.2 应用级角色

每个应用都可以定义自己的业务角色，例如“销售经理”“法务专员”“采购审批人”“交付经理”。

应用级角色与平台级角色不是同一概念。平台级角色决定一个人能否管理平台和应用；应用级角色决定一个人能否参与某个应用中的具体流程节点和资源使用。

V1 的成员授权先只基于角色维度，不引入部门、组织、岗位等组织维度；对象模型需要预留未来扩展这些维度的能力。

### 6.3 角色关系原则

1. 平台级角色和应用级角色分层管理。
2. 应用管理员可以管理本应用角色和成员，但不能越权管理平台角色。
3. 一个用户可以同时属于多个应用，并在不同应用中扮演不同业务角色。
4. 权限判断以最小授权原则为准。

## 7. 核心对象模型

本节定义程序设计需要围绕的核心业务对象。

### 7.1 PlatformUser

平台用户对象，包含基础身份信息、注册状态、平台角色、账号状态、所属应用列表和审计信息。

关键状态包含：待审批、已激活、已禁用、已锁定。

### 7.2 Application

应用对象代表一个业务域工作台，包含应用名称、描述、图标、归属管理员、应用工作空间、应用角色定义、应用资源清单、流程定义集和发布信息。

应用是平台中的一级治理单位。

### 7.3 AppRole

应用角色对象定义应用内业务职责和授权边界，可被绑定到流程节点、资源可见范围和操作动作。

### 7.4 ResourceCatalogItem

资源目录对象用于统一编目 skill、MCP、知识库、LLM 模板等平台能力。

每个资源都必须至少包含：资源类型、名称、描述、版本、归属范围、状态、可见角色、可调用角色、发布信息。

### 7.5 WorkflowDefinition

流程定义对象属于某个应用，描述流程元信息、流程图结构、节点定义、节点之间的流转关系、输入输出契约、发布状态和版本。

### 7.6 WorkflowInstance

流程实例对象代表某次真实业务执行，包含实例编号、来源应用、关联流程定义版本、发起人、当前状态、当前节点集合、业务数据快照、审计轨迹和结束原因。

### 7.7 WorkflowNodeDefinition

流程节点定义对象描述某个节点的类型、责任角色、输入要求、输出要求、可用资源、交互方式、校验规则和后续路由规则。

### 7.8 Task

待办对象是人工节点在实例运行中的工作单元，包含处理人、状态、上下文、截止时间、处理动作、提交结果和处理历史。

### 7.9 AuditEvent

审计事件对象记录平台和应用中的关键操作，包括操作主体、操作对象、操作时间、操作前后摘要、来源和结果。

## 8. 平台信息架构

平台从信息架构上分为五层。

### 8.1 平台治理层

负责用户、角色、应用、公共资源、审批、审计和全局配置。

### 8.2 应用管理层

负责某个应用的工作空间、角色、成员、流程、资源和版本发布。

### 8.3 流程执行层

负责流程定义、流程实例、节点流转、待办生成、自动执行和状态推进。

### 8.4 AI 交互层

负责人在待办处理过程中的自然语言交互、任务理解、辅助生成、结果整理、校验反馈和确认提交。

### 8.5 集成资源层

负责平台公共或应用私有的 MCP、skill、知识库、LLM 能力编目、授权、发布和调用。

## 9. 认证与授权设计

### 9.1 注册与审批

V1 支持用户注册后进入待审批状态，只有系统管理员审批通过后账户才可登录平台。

审批动作至少需要记录审批人、审批意见、审批时间和最终结果。

### 9.2 平台权限域

平台权限至少覆盖以下能力域：

1. 用户审批与账号管理。
2. 平台角色分配。
3. 应用创建与归档。
4. 公共资源维护与发布。
5. 平台级审计查看。

### 9.3 应用权限域

应用权限至少覆盖以下能力域：

1. 应用基础信息维护。
2. 应用角色定义与授权。
3. 流程定义编辑与发布。
4. 应用资源维护与授权。
5. 流程实例查看与干预。
6. 应用审计查看。

### 9.4 资源权限模型

每个资源需要至少区分三类权限：

1. 可见权限：谁能在界面中看到该资源。
2. 可配置权限：谁能在流程或节点中绑定该资源。
3. 可调用权限：谁能在任务执行中实际使用该资源。

### 9.5 权限判断原则

一个用户在某次任务中是否能够使用某资源，需要同时满足以下条件：

1. 用户可访问该应用。
2. 用户在该应用中具备相应角色。
3. 当前节点允许使用该资源。
4. 该资源对该角色开放调用。

## 10. 应用模型设计

### 10.1 应用基础字段

应用至少包含以下字段：

1. 应用名称。
2. 应用描述。
3. 应用图标。
4. 应用唯一标识。
5. 应用状态。
6. 应用管理员列表。
7. 应用工作空间标识。
8. 应用角色集合。
9. 应用资源目录。
10. 应用流程定义集合。

### 10.2 应用工作空间

每个应用拥有自己的工作空间，用于承载应用内流程运行所需的配置、脚本、资产和过程文件。

应用工作空间是应用级隔离的重要基础，但其产品含义应明确为“应用运行与管理空间”，而不是通用个人文件盘。

### 10.3 应用首页

用户进入应用后，应能看到以下核心信息：

1. 我在该应用中的待办。
2. 我参与的流程实例。
3. 应用内可进入的业务入口。
4. 应用总体运行状态摘要。
5. 与我角色相关的资源和知识入口。

### 10.4 应用生命周期

应用支持：草稿、启用中、停用中、已归档。

停用中的应用不再允许新流程发起，但保留存量实例查看和审计能力。

## 11. 资源治理模型

### 11.1 资源类型

V1 统一治理以下资源类型：

1. Skill。
2. MCP。
3. 知识库。
4. LLM 能力配置或可用模型入口。

### 11.2 资源归属范围

资源分为两级：

1. 平台公共资源，由系统管理员维护，可被多个应用复用。
2. 应用私有资源，由应用管理员维护，仅在本应用内可见或可调用。

### 11.3 资源元数据

每个资源至少应具备以下元数据：

1. 名称。
2. 类型。
3. 描述。
4. 版本。
5. 归属范围。
6. 状态。
7. 负责人。
8. 权限配置。
9. 最近发布时间。
10. 适用说明。

### 11.4 资源状态

资源支持：草稿、已发布、已下线。

草稿资源不能进入正式流程调用；已下线资源不能再被新流程版本引用。

### 11.5 资源版本原则

资源版本必须可识别且可回溯。流程定义在发布时应固定其引用的资源版本，避免流程运行行为因资源漂移而不可解释。

这是平台可审计和可复现的关键要求。

应用私有脚本采用轻量治理模式，不单独设计复杂的审核流和发布体系。脚本由应用管理员直接维护；流程发布时仍需固定其所引用的脚本修订标识或脚本快照，以保证运行结果可追溯。

## 12. 流程模型设计

### 12.1 流程定义目标

流程定义用于描述一类业务的执行规则，包括从哪里发起、经过哪些节点、每个节点由谁处理、每个节点需要什么输入、允许使用什么资源、输出如何被校验以及流程在什么条件下结束。

### 12.2 V1 节点类型

V1 仅支持以下基础节点类型：

1. 开始节点。
2. 人工节点。
3. 自动节点。
4. 条件分支节点。
5. 合流节点。
6. 结束节点。

会签、串签、转交和加签作为人工节点内部处理策略存在，V1 不引入大量独立 BPMN 元素。

V1 支持会签、串签、转交和加签，但这些能力先作为人工节点的处理策略存在，而不是扩展为独立的 BPMN 节点家族。

### 12.3 节点责任定义

每个节点必须明确以下信息：

1. 节点名称和说明。
2. 节点类型。
3. 责任角色或责任人解析规则。
4. 输入契约。
5. 输出契约。
6. 可用资源。
7. 可执行动作。
8. 完成判定条件。
9. 路由规则。

### 12.4 输入输出契约

每个节点都必须声明输入和输出契约。

输入契约定义当前节点要消费哪些数据，输出契约定义当前节点必须产生哪些结果。

契约区分为两部分：

1. 结构化字段，例如金额、客户名称、审批结论、风险等级、推荐动作。
2. 非结构化内容，例如说明文本、附件、引用资料、对话摘要。

没有输入输出契约的节点，只适合实验，不适合企业正式流程。

### 12.5 路由规则

流程路由至少支持：

1. 顺序流转。
2. 条件分支。
3. 正常结束。
4. 驳回或退回指定节点。

退回规则必须在产品上定义清楚，否则人工节点之间会出现责任不清和数据口径混乱的问题。

V1 允许退回到任意历史节点，但每次退回都必须记录退回原因、目标节点、操作人和退回时的数据快照。

### 12.6 流程版本与发布

流程定义需要支持版本化。

草稿版本可编辑但不可正式发起；已发布版本可被新实例使用；历史实例继续绑定其创建时的流程版本。

V1 不支持直接修改已发布版本且影响运行中实例的能力。

## 13. 人工节点与待办设计

### 13.1 待办是用户工作的核心入口

用户登录平台后，首先看到的应该是统一待办视图，而不是应用列表本身。

应用列表是工作域入口，待办中心才是工作流入口。

### 13.2 待办列表核心字段

每条待办至少展示：

1. 待办标题。
2. 所属应用。
3. 所属流程。
4. 当前节点名称。
5. 发起人或上游来源。
6. 优先级。
7. 截止时间。
8. 当前状态。
9. 最近更新时间。

### 13.3 待办详情页核心内容

待办详情页至少包含以下区域：

1. 当前任务目标。
2. 上游节点输入。
3. 当前节点输入要求。
4. 当前节点输出要求。
5. 可用资源列表。
6. AI 协作区。
7. 用户最终提交区。
8. 历史处理轨迹。

### 13.4 人工节点处理动作

V1 支持以下标准动作：

1. 开始处理。
2. 暂存。
3. 提交。
4. 退回。
5. 转交。
6. 请求补充信息。

不同业务节点可以按配置裁剪动作集合，但标准动作模型应统一。

### 13.5 人工节点结果提交

用户在人工节点中完成处理后，应提交结构化结果和可选的说明性内容。

提交前，平台应基于节点输出契约进行校验，并明确向用户展示哪些内容缺失、哪些内容格式不符、哪些信息不足以进入下一个节点。

## 14. AI 交互设计

### 14.1 AI 不是独立聊天窗口，而是任务处理助手

在企业流程场景中，AI 的主要职责不是开放式闲聊，而是帮助用户理解任务、整理上下文、引用知识、调用获授权资源、生成候选结果并协助用户形成可提交的正式输出。

### 14.2 AI 可见上下文

AI 在当前任务中可见的上下文应至少包括：

1. 当前应用信息。
2. 当前流程和节点定义摘要。
3. 上游节点输出。
4. 当前节点输入数据。
5. 当前用户已被授权访问的资源。
6. 当前节点允许调用的资源。

AI 不应默认可见该应用的全部数据，更不应越权访问其他应用或平台全局敏感信息。

### 14.3 AI 支持能力

V1 中 AI 至少应支持：

1. 解释当前任务目标。
2. 总结上游输入。
3. 根据知识库和资源生成处理建议。
4. 生成结构化输出草稿。
5. 检查输出是否满足当前节点要求。
6. 提醒用户潜在缺项和风险。

### 14.4 人机责任边界

在人工节点中，最终提交责任仍归属于用户，AI 的建议不能自动视为最终业务结论。

产品上必须明确体现“AI 生成”和“用户确认提交”之间的责任边界。

## 15. 自动节点设计

### 15.1 自动节点职责

自动节点用于执行不需要人工直接参与的动作，例如调用 MCP 写入外部系统、执行获授权脚本、读取知识源、生成中间结果或完成规则判断。

自动节点允许执行应用私有脚本。应用私有脚本视为应用私有资源的一种，由应用管理员直接维护和绑定。

### 15.2 自动节点配置项

每个自动节点至少应定义：

1. 节点目标。
2. 输入来源。
3. 可调用资源。
4. 预期输出。
5. 失败处理策略。
6. 超时策略。

### 15.3 自动节点失败

自动节点失败后，流程不能进入不可解释状态。

V1 至少需要定义三种产品行为：

1. 自动重试。
2. 转人工处理。
3. 标记流程异常并等待管理员干预。

## 16. 输出校验与流转规则

### 16.1 校验目标

平台需要确保每个节点的输出足以被下游节点或外部系统消费。

因此，校验的目标不是“判断答案是否完美”，而是“判断当前输出是否达到下一步可执行的最低要求”。

### 16.2 校验时机

至少需要在以下时机进行校验：

1. 人工节点提交前。
2. 自动节点执行后进入下游前。
3. 流程发布前检查节点契约完整性。

### 16.3 校验结果

校验结果至少区分：

1. 通过，可继续流转。
2. 不通过，可说明缺失项并要求补充。
3. 存疑，需要人工确认后继续。

### 16.4 校验反馈

反馈必须能被业务用户看懂，不能只返回技术错误信息。

例如应直接告诉用户“缺少审批结论字段”或“未提供可写回 ERP 的订单号”，而不是只返回抽象失败代码。

## 17. 流程实例与运行态设计

### 17.1 实例状态

流程实例支持以下状态：

1. 运行中。
2. 已完成。
3. 已终止。
4. 异常中。
5. 已挂起。

### 17.2 节点状态

节点实例支持以下状态：

1. 未开始。
2. 处理中。
3. 已完成。
4. 已退回。
5. 已跳过。
6. 异常。

### 17.3 运行态可观测性

应用管理员至少应能查看：

1. 每个流程实例当前停留在哪个节点。
2. 每个待办分配给了谁。
3. 节点执行是否成功。
4. 外部调用是否失败。
5. 流程是否卡住以及卡住原因。

管理员对运行中实例的干预边界，V1 至少支持跳转节点、终止实例和重试自动节点。这些动作只对具备相应权限的管理员开放，并且必须进入审计范围。

## 18. 审计与合规要求

以下行为必须进入审计范围：

1. 用户注册审批。
2. 平台角色分配。
3. 应用创建、启停、归档。
4. 应用角色授权。
5. 资源创建、发布、下线。
6. 流程创建、修改、发布、停用。
7. 人工节点提交、退回、转交。
8. 自动节点关键调用结果。
9. 流程终止和管理员干预。

审计记录至少应满足“谁在什么时候对什么对象做了什么，结果如何”的基本要求。

## 19. 非功能性产品要求

本节不定义技术方案，只定义产品层面对系统能力的要求。

1. 权限判定必须稳定且可解释。
2. 历史流程实例必须可追溯到其当时绑定的流程版本和资源版本；应用私有脚本至少需要可追溯到流程发布时绑定的脚本修订标识或脚本快照。
3. 平台关键操作必须具备审计记录。
4. 用户处理任务时应能稳定看到一致的上下文。
5. 自动节点失败不能悄悄吞掉，必须进入可见状态。
6. 平台需要支持逐步扩展更多节点类型和资源类型。

## 20. V1 范围

### 20.1 V1 必做能力

1. 用户注册、审批、登录和平台角色分配。
2. 应用创建、应用管理员管理和应用基础信息维护。
3. 应用角色定义和成员授权。
4. 公共资源与应用私有资源编目。
5. 流程定义、草稿保存、版本发布。
6. 基础流程画布和基础节点类型。
7. 统一待办中心。
8. 人工节点 AI 协作处理界面。
9. 自动节点调用与失败可见化。
10. 节点输入输出契约与提交校验。
11. 流程实例查询和基础审计。

### 20.2 V1 暂不纳入核心范围

1. 完整 BPMN 标准兼容。
2. 复杂事件网关和补偿事务。
3. 多租户 SaaS 运营能力。
4. 复杂组织架构和矩阵式汇报链建模。
5. 高级流程挖掘和流程仿真。
6. 应用商店和对外商业生态。

## 21. 关键产品规则

作为企业信息化平台，以下规则纳入产品定义。

### 21.1 先定义“节点数据契约”，再定义画布

很多流程产品先做漂亮画布，后补数据契约，最终会导致流程能画但不能稳定运行。DSH 应反过来，先把节点输入输出、责任角色、资源权限和提交校验定义清楚，再做画布表达。

### 21.2 先做“受约束流程引擎”，不要直接追求完整 BPM

企业真正大量落地的流程并不需要 BPMN 全量能力。V1 做少量高频元素，反而更容易保证可解释、可调试、可审计。

### 21.3 资源发布必须和流程发布解耦

资源可以独立演进，但流程发布时必须固定所依赖的资源版本。否则流程的运行结果将不可复盘。

### 21.4 待办中心优先级高于应用门户

真正推动员工日常工作的不是“进入哪个应用”，而是“今天有哪些任务要完成”。因此待办中心应作为首页级入口。

### 21.5 审计和管理员干预能力必须首版具备

没有管理员干预、异常查看和审计回溯，流程平台很难在真实企业环境落地。

## 22. 结论

DSH 企业版的本质不是“把 Agent 提供给多人使用”，而是“把企业中跨系统、流程驱动、需要人工参与的工作统一收敛到一个 AI 原生的平台中”。

这个平台的核心对象不是对话，而是应用、流程、节点、待办、资源和审计。

只要产品设计坚持“流程主线、人工节点优先、资源治理先行、审计闭环内建”的原则，DSH 就有机会从通用 Agent Harness 演进为可进入企业内部真实业务场景的 BPIT 平台。
