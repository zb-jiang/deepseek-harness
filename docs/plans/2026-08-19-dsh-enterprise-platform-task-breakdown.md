## 2. 拆解原则

V1 的任务拆解遵循以下原则：

1. 先打通最小可运行闭环，再叠加复杂动作和治理能力。
2. 先实现平台治理和流程骨架，再实现人工节点高级策略。
3. 先实现后端规则和状态机，再实现 Web 管理界面与运行界面。
4. 每个任务都必须有明确输入、产出、依赖和验收标准。
5. 每个任务都必须能映射到仓库现有包线或新增的明确包线。

## 3. 实现工作流总览

V1 实现按六个工作流组织：

1. 平台身份与治理工作流。
2. 应用、角色与资源工作流。
3. 流程定义与版本工作流。
4. 流程运行时工作流。
5. Web 界面与交互工作流。
6. 审计、监控与验收工作流。

这六个工作流对应开发细化 SPEC 的六个开发域，但更强调实际交付顺序和任务依赖。

## 4. 模块边界与仓库落点

下表定义 V1 主要模块的职责和优先落点。

| 模块 | 主要职责 | 主要落点 |
|---|---|---|
| 平台身份与用户治理 | 注册审批、平台角色、账号状态 | `packages/identity`、`packages/interaction`、`packages/session`、`packages/api`、`packages/web` |
| 应用与成员治理 | 应用、应用管理员、应用角色、成员授权、应用工作空间 | `packages/workspace`、`packages/api`、`packages/web` |
| 资源目录治理 | 公共资源、应用私有资源、资源权限、脚本修订标识 | `packages/skill`、`packages/mcp`、`packages/settings`、`packages/api`、`packages/web` |
| 流程定义与版本 | 流程定义、流程版本、节点定义、契约校验、发布 | `packages/workflow`、`packages/api`、`packages/web` |
| 流程运行时 | 流程实例、节点实例、待办、状态迁移、退回、加签、转交 | `packages/workflow`、`packages/todo`、`packages/session`、`packages/api` |
| 自动节点执行 | 自动节点、私有脚本、外部资源调用、失败处理、重试 | `packages/workflow`、`packages/skill`、`packages/mcp`、`packages/shell`、`packages/jobs` |
| 管理员干预与审计 | 跳转节点、终止实例、重试自动节点、审计记录、运行历史 | `packages/session`、`packages/api`、`packages/web` |
| Web 管理端与任务端 | 管理后台、流程设计 UI、待办中心、任务详情、运行监控 | `packages/web`、`packages/api`、`packages/bundle` |

这里的“主要落点”表示优先责任区，不表示只能改这些包。

## 5. 里程碑定义

V1 分为四个交付里程碑。

### 5.1 M1 平台骨架可用

完成用户、应用、角色、成员、资源目录的基础治理，能够登录、建应用、配角色、分成员、建资源。

### 5.2 M2 流程骨架可运行

完成流程定义、流程版本发布、单人任务流转、待办中心和基础任务提交。

### 5.3 M3 高级动作可运行

完成会签、串签、转交、加签、任意历史节点退回、自动节点失败处理。

### 5.4 M4 管理闭环可验收

完成管理员干预、审计、运行监控和关键验收场景，形成 V1 可验收闭环。

## 6. 工作流一：平台身份与治理

### T1 用户注册与审批

- 目标：实现平台用户注册、待审批、审批通过、禁用和锁定。
- 来源规格：
  - 总 SPEC `9.1 注册与审批`
  - 开发细化 SPEC `4.1 PlatformUser`、`5.1 PlatformUser 状态机`
- 主要产出：
  - 用户对象模型
  - 注册与审批接口
  - 审批审计记录
  - 注册/审批管理 UI
- 依赖：无
- 验收标准：
  - 未审批用户不可登录
  - 审批通过用户可登录
  - 禁用用户无法访问平台动作

### T2 平台角色管理

- 目标：实现系统管理员、应用管理员、普通用户的平台角色分配与校验。
- 来源规格：
  - 总 SPEC `6.1 平台级角色`
  - 开发细化 SPEC `4.1 PlatformUser`
- 主要产出：
  - 平台角色授权接口
  - 角色校验中间层
  - 平台管理界面
- 依赖：T1
- 验收标准：
  - 非系统管理员不能分配平台角色
  - 平台角色变化立即影响可访问能力

## 7. 工作流二：应用、角色与资源

### T3 应用管理

- 目标：实现应用创建、启停、归档、管理员维护和应用工作空间绑定。
- 来源规格：
  - 总 SPEC `10. 应用模型设计`
  - 开发细化 SPEC `4.2 Application`、`5.2 Application 状态机`
- 主要产出：
  - 应用对象模型
  - 应用管理接口
  - 应用基础管理 UI
- 依赖：T2
- 验收标准：
  - 应用创建后默认处于草稿态
  - 已归档应用不可发起新实例

### T4 应用角色与成员授权

- 目标：实现应用角色定义、成员授权和角色维度访问控制。
- 来源规格：
  - 总 SPEC `6.2 应用级角色`、`9.3 应用权限域`
  - 开发细化 SPEC `4.3 AppRole`、`4.4 AppMembership`
- 主要产出：
  - 应用角色对象模型
  - 成员授权接口
  - 成员与角色管理 UI
- 依赖：T3
- 验收标准：
  - 同一用户在同一应用只有一条有效成员记录
  - 无应用成员关系的用户不可访问应用待办

### T5 资源目录与资源权限

- 目标：实现平台公共资源、应用私有资源、资源权限和资源状态管理。
- 来源规格：
  - 总 SPEC `11. 资源治理模型`
  - 开发细化 SPEC `4.5 ResourceCatalogItem`、`5.3 ResourceCatalogItem 状态机`
- 主要产出：
  - 资源目录对象模型
  - 资源管理接口
  - 资源状态流转
  - 资源目录 UI
- 依赖：T3、T4
- 验收标准：
  - 资源具备可见、可配置、可调用三类权限
  - 已下线资源不能被新流程版本绑定

### T6 应用私有脚本治理

- 目标：实现应用私有脚本作为应用私有资源的轻量治理和追溯标识。
- 来源规格：
  - 总 SPEC `11.5 资源版本原则`、`15.1 自动节点职责`
  - 开发细化 SPEC `9.2 私有脚本规则`
- 主要产出：
  - `script` 资源类型支持
  - `revisionRef` 追溯标识
  - 脚本绑定接口
  - 脚本管理 UI
- 依赖：T5
- 验收标准：
  - 流程发布时固定脚本 `revisionRef`
  - 自动节点重试沿用同一 `revisionRef`

## 8. 工作流三：流程定义与版本

### T7 流程定义对象与画布骨架

- 目标：实现流程定义、节点定义、边关系和基础流程画布编辑骨架。
- 来源规格：
  - 总 SPEC `12.1 流程定义目标`、`12.2 V1 节点类型`
  - 开发细化 SPEC `4.6 WorkflowDefinition`、`4.7 WorkflowVersion`、`4.8 WorkflowNodeDefinition`
- 主要产出：
  - 流程定义对象模型
  - 节点与边编辑接口
  - 基础流程画布 UI
- 依赖：T3、T5
- 验收标准：
  - 仅允许 `start/human/auto/condition/merge/end` 六类节点
  - 节点和边结构可保存为草稿

### T8 节点输入输出契约

- 目标：实现节点输入契约、输出契约和发布前校验。
- 来源规格：
  - 总 SPEC `12.4 输入输出契约`、`16.2 校验时机`
  - 开发细化 SPEC `4.8 WorkflowNodeDefinition`、`12. 关键不变量`
- 主要产出：
  - 契约定义模型
  - 契约校验器
  - 契约编辑 UI
- 依赖：T7
- 验收标准：
  - 无输入输出契约的人工/自动节点不可发布
  - 发布校验能定位缺失字段和非法绑定

### T9 流程版本发布

- 目标：实现流程草稿保存、版本号递增、发布冻结和停用。
- 来源规格：
  - 总 SPEC `12.6 流程版本与发布`
  - 开发细化 SPEC `4.7 WorkflowVersion`、`5.4 WorkflowDefinition 状态机`
- 主要产出：
  - 发布接口
  - 发布校验
  - 版本列表 UI
- 依赖：T7、T8、T5、T6
- 验收标准：
  - 已发布版本只读
  - 发起实例只能绑定已发布版本

## 9. 工作流四：流程运行时

### T10 流程实例与节点实例骨架

- 目标：实现流程实例、节点实例、当前有效数据和运行态推进骨架。
- 来源规格：
  - 总 SPEC `7.6 WorkflowInstance`、`17. 流程实例与运行态设计`
  - 开发细化 SPEC `4.9 WorkflowInstance`、`4.10 NodeInstance`
- 主要产出：
  - 实例对象模型
  - 节点激活与推进逻辑
  - 实例状态流转
- 依赖：T9
- 验收标准：
  - 实例永远绑定创建时流程版本
  - 节点推进遵守定义的节点类型和边关系

### T11 单人任务流转

- 目标：实现单人处理人工节点的任务创建、开始处理、暂存、提交和关闭。
- 来源规格：
  - 总 SPEC `13. 人工节点与待办设计`
  - 开发细化 SPEC `4.11 Task`、`5.7 Task 状态机`、`6.1 单人处理`、`7.1-7.3`
- 主要产出：
  - 任务对象模型
  - 待办创建逻辑
  - 单人任务接口
- 依赖：T10
- 验收标准：
  - 人工节点激活后生成待办
  - 提交后节点完成并进入下一步

### T12 会签

- 目标：实现会签节点的并行任务创建、聚合输出和完成判定。
- 来源规格：
  - 总 SPEC `12.2 V1 节点类型`
  - 开发细化 SPEC `6.2 会签`
- 主要产出：
  - 会签任务生成逻辑
  - 聚合结果逻辑
  - 节点完成判定逻辑
- 依赖：T11
- 验收标准：
  - 所有并行任务提交后节点才完成
  - 节点输出为聚合数组

### T13 串签

- 目标：实现串签节点的顺序任务创建和结果链保留。
- 来源规格：
  - 总 SPEC `12.2 V1 节点类型`
  - 开发细化 SPEC `6.3 串签`
- 主要产出：
  - 串签任务链
  - 顺序推进逻辑
  - 顺序结果聚合
- 依赖：T11
- 验收标准：
  - 只生成当前序位任务
  - 最后一个任务提交后节点完成

### T14 转交

- 目标：实现任务转交和原任务失效规则。
- 来源规格：
  - 总 SPEC `13.4 人工节点处理动作`
  - 开发细化 SPEC `6.4 转交`、`7.5 转交`
- 主要产出：
  - 转交接口
  - 新任务创建逻辑
  - 转交审计
- 依赖：T11
- 验收标准：
  - 原任务状态变为 `transferred`
  - 新任务继承原输入快照和上下文

### T15 加签

- 目标：实现串行加签、处理链更新和完成条件重算。
- 来源规格：
  - 总 SPEC `12.2 V1 节点类型`
  - 开发细化 SPEC `6.5 加签`、`7.6 加签`
- 主要产出：
  - 加签接口
  - 处理链更新逻辑
  - 加签审计
- 依赖：T13
- 验收标准：
  - 只支持串行加签
  - 加签后节点完成条件随处理链变化

### T16 任意历史节点退回

- 目标：实现退回到任意历史节点、当前数据带回、下游失效和历史保留。
- 来源规格：
  - 总 SPEC `12.5 路由规则`
  - 开发细化 SPEC `7.4 退回`、`8. 退回规则`
- 主要产出：
  - 退回接口
  - 数据基线回带逻辑
  - 下游节点失效逻辑
  - 退回审计
- 依赖：T11、T12、T13
- 验收标准：
  - 只允许退回到历史节点
  - 下游活动任务全部关闭
  - 历史记录不删除

## 10. 工作流五：自动节点与管理员干预

### T20 终止实例

- 来源规格：
  - 总 SPEC `17.3 运行态可观测性`

- 依赖：T10、T11

### T21 重试自动节点

- 来源规格：

## 13. 并行开发建议

在资源允许的情况下，建议按以下方式并行：

1. 一组负责 `T1-T6` 平台治理与资源治理。
2. 一组负责 `T7-T10` 流程定义和实例骨架。
3. 一组负责 `T22-T24` Web 界面，但必须跟随后端任务的对象与状态机定义。
4. 一组负责 `T25-T26` 审计和验收自动化，在关键动作完成后插入。

会签、串签、加签、退回和管理员干预属于高耦合动作，建议由同一小组连续实现。

## 14. 交付顺序

推荐交付顺序如下：

1. 交付 `T1-T6`，形成平台治理最小骨架。
2. 交付 `T7-T11`，形成单人流程闭环。
3. 交付 `T12-T16`，形成人工节点高级动作闭环。
4. 交付 `T17-T21`，形成自动节点与管理员干预闭环。
5. 交付 `T22-T25`，形成完整管理与使用界面。
6. 交付 `T26`，形成最终验收出口。

## 15. 每阶段完成定义

### 15.1 平台骨架完成

满足以下条件即视为平台骨架完成：

1. 用户、平台角色、应用、应用角色、成员和资源目录可在界面中完成管理。
2. 资源权限能阻止未授权用户访问资源。

### 15.2 流程骨架完成

满足以下条件即视为流程骨架完成：

1. 管理员可以创建、发布流程版本。
2. 普通用户可以发起实例并完成单人任务处理。

### 15.3 高级动作完成

满足以下条件即视为高级动作完成：

1. 会签、串签、转交、加签和退回全部可运行。
2. 自动节点失败策略全部可运行。

### 15.4 管理闭环完成

满足以下条件即视为管理闭环完成：

1. 管理员可以跳转节点、终止实例、重试自动节点。
2. 审计和运行监控完整可用。
3. 最小验收场景全部通过。

## 16. 一致性检查清单

在每个里程碑结束时，必须用以下清单检查三份文档和实际实现是否一致：

1. 总 SPEC 中出现的每个核心对象，开发细化 SPEC 和代码中都能找到对应实体。
2. 总 SPEC 中出现的每个标准动作，开发细化 SPEC 和代码中都能找到对应语义。
3. 开发细化 SPEC 中定义的每个状态机，代码实现和测试用例都能验证。
4. 任务拆解文档中的每个任务，都能回指前两份规格中的来源章节。
5. 代码实现中若出现新的产品规则，必须先回写上位规格，再进入任务拆解和实现。
