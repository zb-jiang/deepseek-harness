# 组织维度审批路由设计(行政线 × 角色)

## 1. 背景与问题

当前 userTask 待办分配链路:`candidateRoleId` → `findActiveUserIdsByRoleId` 查 `app_memberships` → 候选=**全应用**该角色成员,再经 SoD 过滤后多实例逐人 assignee。

`app_memberships(app_id, user_id, role_ids[])` 是应用级扁平映射,没有组织维度,导致:

1. **审批隔离做不到**:A 部门员工提交,全公司该角色成员都收到待办;跨部门越权可见。
2. **多套流程复制的代价**:按部门隔离只能为每个部门复制一套流程定义(N 部门=N 份副本),而 `bpmn_process_key` 查重约束要求每套不同 key,流程治理碎片化、实例统计分裂。
3. **超时升级同样全局**:`escalateToRoleId` 升到的是全公司该角色成员。
4. **SoD 只防"本人审自己"**,防不了"A 部门经理审 B 部门的单"。

对照 `docs/plans/bpm_role_relationships_overview.html` 的 7 项关系模式:②SoD ⑤超时升级 ⑦共享池已支持;本次补的是 **⑥ 组织层级路由**,并明确 **① 角色继承不做**(行政线层级语义替代角色父子关系,角色保持扁平)。

## 2. 模型总纲:范围(横坐标) × 目标角色(纵坐标)

两个正交维度定位审批人:

- **组织树** = 行政线:节点是部门名称,每个节点配一个负责人;一个人 = 在哪个部门(全局维度) × 在该应用是什么职位(应用维度)。
- **范围**(在哪条线上找):同行政线 / 指定部门 / 全公司。
- **目标角色**(找什么人):实体角色(经理/总监等指定职位)或虚拟角色(上一级等,动态计算)。

维度归属:**组织树是全局的**(公司级,一套组织架构所有应用共享,由 system_admin 在平台级维护);**角色是应用级的**(`app_roles` 不动)。组织范围只是给候选解析加过滤维度,两个维度互不侵入。

### 2.1 概念定义

- **行政线**:组织树从申请人所在部门到根的链。部门树从下往上回溯代表线性"行政线"。
- **实体角色**:指定的职位(应用角色列表中选)。存量流程的 `candidateRoleId` 就是实体角色。
- **虚拟角色**:不指定职位,运行时动态取**那一级部门的负责人**(`org_units.head_user_id`)。枚举:`parent`(上一级)/`grandparent`(上两级)/`child`(下一级)/`grandchild`(下两级)。锚点分场景(双锚点):**待办分配锚定申请人**(申请人部门起算,层级自适应——小王提交"上一级"→A部门负责人张三,张三提交"上一级"→华东区负责人老周);**超时升级锚定当前审批人**("审批人超时,审批人的上级接管")。
- **部门负责人**:组织树节点的属性,治理数据,建部门时指定。

### 2.2 组合矩阵

| 场景 | 范围 | 目标角色 | 语义 |
| --- | --- | --- | --- |
| 员工报销经理批、经理报销总监批(审批人永远是提报人上一级) | 同行政线 | 虚拟:parent | 申请人父部门负责人 |
| 常规逐级职位审批 | 同行政线 | 实体:经理 | 从申请人部门**从下往上找第一个该职位**(跳过申请人本人) |
| 大额上两级加审 | 同行政线 | 虚拟:grandparent | 申请人祖父部门负责人 |
| 总经理发文,各部门负责人会签 | 同行政线 | 虚拟:child | 申请人直接下级**所有部门**的负责人(扇出,配会签/单签) |
| 财务复核(共享服务中心) | 指定部门 | 实体:经理 | 指定部门子树内的该角色成员 |
| 全公司统一岗位终审 | 全公司 | 实体:总经理 | 该角色全部成员 |
| 存量流程(无 orgScope) | 全公司(缺省) | 实体角色 | **行为完全不变,向后兼容** |

UI 细节:选了虚拟角色,范围自动锁定"同行政线"(置灰)——虚拟角色本身即在行政线上相对移动,跨线无意义。

### 2.3 示例组织树

```
总公司(负责人:马总)
├── 华东区(负责人:老周)
│   ├── A 部门(负责人:张三;员工:小王)
│   └── B 部门(负责人:李四)
└── 财务部(负责人:钱姐)
```

报销流程四个节点(同一套流程全公司共用):

| 节点 | 配置 | 谁审 |
| --- | --- | --- |
| 直属审批 | 虚拟:parent | 小王提交→张三;张三提交→老周 |
| 大额加审 | 虚拟:grandparent | 小王提交→马总(华东区负责人老周之上) |
| 财务复核 | 实体:经理 + 指定部门:财务部 | 钱姐(财务部经理角色成员) |
| 总经理终审 | 实体:总经理 + 全公司 | 马总 |

## 3. 数据模型

建表 SQL 与执行步骤见 `docs/plans/2026-08-19-supabase-setup-guide.md` §11(手工执行)。

- **org_units**(public schema):组织树。`id / name / parent_id(自引用,null=根) / head_user_id(部门负责人,引用 platform_users) / sort_order / created_at`。同级同名唯一(coalesce 表达式索引,同 kb_folders 惯例);循环引用应用层校验(同 app_roles 惯例)。RLS 启用但不给 authenticated 策略(治理读写只走 JDBC 超级用户,同 applications 模式)。
- **org_unit_members**(public schema):员工×部门多对多映射。`org_unit_id / user_id`,联合唯一;员工可属 0..N 个部门。指定/更换部门负责人时自动 upsert 一行(head 必然有部门归属);部门侧移除成员时若该人是 head 则阻止。RLS 同 org_units。
- **platform_users.org_unit_id**:~~主部门单列~~ **已废弃删除**(存量迁移:非空 org_unit_id 逐行插入 org_unit_members 后删列)。隶属关系统一在映射表,一个事实一个家;审批路由的锚点不再读静态主部门,改为**发起时动态选择身份**(§5.1)。

## 4. BPMN 扩展

`dsh:` 命名空间(`http://dsh.ai/bpmn`),userTask 的 `dsh:assignmentRule` 扩展属性:

```xml
<!-- 实体角色,存量无 orgScope = 全公司,行为不变 -->
<dsh:assignmentRule candidateRoleId="..." />

<!-- 实体角色 + 同行政线 -->
<dsh:assignmentRule candidateRoleId="..." orgScope="sameLine"/>

<!-- 虚拟角色(隐含同行政线) -->
<dsh:assignmentRule virtualRole="parent"/>  <!-- parent / grandparent / child / grandchild -->

<!-- 实体角色 + 指定部门 -->
<dsh:assignmentRule candidateRoleId="..." orgScope="fixedUnit" fixedUnitId="..."/>
```

属性互斥规则:`candidateRoleId` 与 `virtualRole` 二选一;`virtualRole` 时不允许 orgScope/fixedUnitId;`orgScope="fixedUnit"` 时 `fixedUnitId` 必填。发布校验按此检查 + 指定部门存在性 + 实体角色存在性(现有校验)。

## 5. 解析算法

### 5.1 启动注入与发起身份选择

web-console 启动实例时注入应用隔离变量扩为四个:`dsh_applicant_user_id / dsh_app_id / dsh_workflow_definition_id / dsh_applicant_org_unit_id`(**发起身份部门,启动时快照**)。

发起身份部门来源于**发起时的动态选择**,而非静态主部门:

- **发起入口**:流程在 DSH 员工端由员工在新的 AI 对话中发起;web-console 提供 API 供外部(员工端本地 webserver 代理)发起。start 端点权限从 system_admin/app_admin 扩展到**应用成员**(app_memberships 成员可发起所属应用的流程,员工端发起的前提)。
- **位置查询 API**:`GET /api/runtime/my-org-positions` 返回当前登录用户的组织位置列表(部门 id/名称/到根路径);DSH 员工端把它注入 AI 上下文——员工对 AI 发起流程时,AI 发现多位置先问"以哪个身份发起"。
- **start 请求体**加 `orgUnitId`(发起身份):
  - 映射表 **0 个部门**:流程含 sameLine 节点 → 启动报错(同 §5.3);不含 → 正常启动,不注入第四变量。
  - **唯一部门**:自动采用该身份,`orgUnitId` 可不传(传了必须匹配,防伪造)。
  - **多个部门**:`orgUnitId` **必传**(员工端/管理台选择后传入);未传报错"存在多个组织身份,请选择发起身份"。
  - **防伪造**:`orgUnitId` 必须在发起人的 org_unit_members 中,否则拒绝。
- **管理台发起界面**同样提供身份下拉(拉取 my-org-positions);发起人无部门时该流程含 sameLine 节点则启动报错。

### 5.2 候选解析(引擎侧统一组件)

三处解析点统一走同一候选解析器(新增 `DshCandidateResolver`):

- `DshMultiInstanceSetupListener`(节点 start 建候选)
- `DshTaskListener` SoD 过滤(沿用现有 not-applicant / mutex-node,在解析结果上执行)
- `DshTaskEscalationDelegate`(超时升级目标同样支持虚拟角色/范围。**锚点与待办分配不同**:超时升级的虚拟角色锚定**当前审批人**——升级本义是"审批人超时,审批人的上级接管";若锚定申请人,"申请人的上一级"会指回审批人自己,语义失效。**审批人也可能多部门**:升级锚点取该待办创建时写入的任务局部变量 `dsh_assignment_org_unit`(解析出该 assignee 时依据的部门,见下);局部变量缺失时(global 场景或存量任务)回退按 assignee 反查 org_unit_members——唯一部门直接用,0 个或多个部门报错 fail loud,不静默猜)

解析流程:读 `dsh_applicant_org_unit_id` 定位申请人节点 → 按范围×角色查 `org_units`/`org_unit_members`/`app_memberships` → 候选集合 → SoD 过滤 → 快照写 `dsh_candidates_<nodeDefKey>` → 多实例逐人 assignee,并把**解析出该 assignee 的部门**写任务局部变量 `dsh_assignment_org_unit`(超时升级锚点;virtual/sameLine/fixedUnit 均有明确解析部门)。

**部门成员判定走 org_unit_members 多对多映射**(员工跨部门任职时,各隶属线的 sameLine/fixedUnit 待办都能派到);虚拟角色的"负责人"仍取 `org_units.head_user_id`(治理属性,单值)。

**候选在待办创建那一刻快照**,运行中组织调整不影响已建待办(与现有设计一致)。

### 5.3 边界规则

启动校验(精确到需要的节点):流程含**同行政线**范围节点(虚拟角色或 sameLine 实体角色)→ 申请人映射表必须有部门且发起身份明确(§5.1 的 0/N 部门规则),否则启动报错;节点全是指定部门/全公司 → 不要求申请人有部门。

空候选区分"组织结构到顶"与"数据没配全":

| 情况 | 性质 | 行为 |
| --- | --- | --- |
| 虚拟 parent/grandparent,申请人已无父/祖父部门 | **结构到顶** | **节点自动通过**(记审计"审批人到顶自动通过"),流程继续 |
| 申请人有部门,父部门没配负责人 | 数据缺失 | 报错,指明"XX 部门未配置负责人" |
| 实体角色 + sameLine,整条线没有该职位 | 配置/数据问题 | 报错(该场景应配虚拟角色,配实体角色是设计错误) |
| 虚拟 child/grandchild 扇出为空 | 配置错误 | 报错(向下扇出明确预期"有人要签",空说明流程配错或组织没建全) |
| 超时升级虚拟 parent/grandparent,当前审批人已是组织顶点 | 结构到顶 | **无处可升,保持原审批人**(记审计"升级到顶任务保留"),不自动通过、不报错;需要干预走管理员通道 |
| 超时升级锚点回退(global/存量任务)且审批人映射表 0 个或多个部门 | 锚点歧义 | 报错 fail loud("审批人组织身份不唯一,无法定位升级链"),不静默取某一个 |
| 指定部门 / 全公司范围空候选 | 数据缺失 | 报错(现有行为) |

核心原则:**向上的尽头是组织的自然顶点,自动通过;其余的空都是数据或设计问题,报错不静默**。自动通过只发生在"向上找、且确实到顶"这一种情况。

### 5.4 "跳过申请人本人"

实体角色 + sameLine 从申请人部门从下往上找第一个匹配职位时,**跳过申请人本人后继续上翻**("自己的审批人永远不是自己",符合直接主管直觉);虚拟角色取部门负责人时同样排除申请人本人后判空(负责人恰是申请人 → 上翻,虚拟 parent 情况下视为该层到顶继续向上)。

## 6. UI 设计(web-console)

### 6.1 部门管理页(新增)

- 树形展示组织架构,节点增删改、拖拽或选父部门调整层级。
- 每个节点指定**负责人**(从 platform_users 用户列表选)。

### 6.2 用户管理页(增强)

- 每个用户维护**所属部门(多选)**(部门树多选,可空,写 org_unit_members);列表列显示部门标签清单。

### 6.3 流程设计器 userTask 属性面板(增强)

候选角色配置区扩展:

- **审批范围**下拉:同行政线 / 指定部门 / 全公司(缺省全公司=现状)。
- **目标角色**:实体角色下拉(现有)或切换为虚拟角色(上一级/上两级/下一级/下两级);选虚拟角色时范围锁定"同行政线"置灰。
- 选"指定部门"时出现部门树选择器。

### 6.4 员工端(发起交互)

- 员工端(DSH Electron,enterprise profile)上下文注入**当前登录人的组织位置**(经 web-console `GET /api/runtime/my-org-positions`,本地 webserver 代理调用):员工在新的 AI 对话中发起流程时,AI 已知其全部身份。
- **身份选择交互**:员工在组织树中有多个位置时,AI 先确认"本流程实例以哪个身份发起"(选择后作为 `orgUnitId` 调 start API);唯一位置或无位置(流程不含 sameLine 节点)免选择。
- 待办推送照旧 my-tasks,候选变化对员工透明。

## 8. 决策记录

1. **"同部门"与"本部门及上级"合并为"同行政线"**:从申请人部门从下往上找第一个匹配,部门岗位没配齐时自动找最近的上级责任人,不报错。
2. **角色树不做**:行政线承担层级语义,角色保持扁平;"上一级"是虚拟角色(取父部门负责人)而非角色父子关系。
3. **虚拟角色单独使用即"那一级的负责人"**:不引入"虚拟层级 × 实体角色"组合;"上两级+经理"这类配置用"实体角色+同行政线"表达。
4. **范围与角色是横纵坐标**:范围管"在哪条线上找"(同线/跨线),角色管"找什么人"(实体职位/虚拟相对层级)。
5. **审批人配置 = 申请人相对定位 + 职位**,而非绝对用户指定;要精确到单人用指定部门+唯一角色成员+单签,或后续再做指定用户。
6. **缺省 orgScope=全公司**:存量流程零影响。
7. **申请人无部门的启动校验精确到节点**:仅含同行政线节点才要求;指定部门/全公司节点不要求。
8. **向上到顶自动通过、其余空候选报错**:结构到顶(总经理报销)是自然语义,数据缺失静默回退会让隔离形同虚设。
9. **组织树全局、角色应用级**:组织树是公司级共享治理数据(所有应用共用一套行政线,平台级维护),app_roles 不动;组织范围只是候选解析的过滤维度,跨应用公司级职位留二期。
10. **兼岗多归属改为映射表 + 发起身份选择**(取代初版"主部门单值留二期"):org_unit_members 多对多记录员工全部部门归属;审批路由锚点不再是静态主部门,而是发起流程实例时**动态选择的身份**(多位置必选、唯一自动、防伪造校验归属);sameLine/fixedUnit 的部门成员判定走映射表,跨部门任职各线待办都能派到。
11. **虚拟角色双锚点**:待办分配锚定申请人(层级自适应:员工与经理提交同一节点自动错开审批链);超时升级锚定当前审批人(升级本义是审批人的上级接管,锚申请人会指回审批人自己)。升级到顶无处可去时保持原审批人并记审计,不自动通过。
12. **部门负责人自动入成员映射**:指定/更换 head 时自动 upsert org_unit_members(负责人必然有部门归属,组织位置语义完整);移除成员时若其为本部门 head 则阻止。
13. **升级锚点优先任务局部变量**:派发待办时写 `dsh_assignment_org_unit`(解析出该 assignee 依据的部门),超时升级优先读它;缺失时回退映射表且要求唯一(0 个或多个部门报错),不静默猜身份。
